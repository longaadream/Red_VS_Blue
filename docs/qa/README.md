# 测试、调试与质量保证

状态：草案  
负责人：项目负责人  
适用版本：重构版本

本目录用于保存测试场景、人工回归清单、Bug 复现记录、已知问题和构建验收结果。

当前首要目标是减少重复人工操作，让问题能够稳定复现、快速定位并可靠验证。

## Bug 报告最低要求

每个 Bug 应尽量包含：

- 游戏版本或 Git 提交编号。
- 操作系统和运行环境。
- 使用的初始场景或存档。
- 当前回合和游戏阶段。
- 随机种子（如果相关）。
- 可重复执行的操作步骤。
- 期望结果。
- 实际结果。
- 错误日志。
- 失败前后的关键状态。
- 截图或录屏。
- 复现频率。

无法稳定复现时，应明确写明已尝试的条件和出现概率，不能只填写“偶尔发生”。

## Bug 修复流程

1. 确认问题是否属于当前版本。
2. 建立最小复现步骤。
3. 找到触发问题的状态和输入。
4. 尽量先建立失败测试或可重复回放。
5. 修复根本原因。
6. 验证原问题已经消失。
7. 验证相邻规则没有受到破坏。
8. 把复现流程加入回归清单。
9. 在 PR 中附上修复前后的证据。

## 测试层级

### 快速检查

用于每次 PR：

- 类型检查。
- Lint 或静态检查。
- 受影响模块的单元测试。
- 核心规则的最小验证。

### 游戏模拟

用于规则和数值变更：

- 固定随机种子。
- 固定初始状态。
- 固定命令序列。
- 状态快照比较。
- 关键不变量检查。

### Electron 冒烟测试

用于桌面应用：

- 应用能够启动。
- 能够进入主界面。
- 能够创建或读取游戏。
- 能够完成核心操作。
- 能够正常关闭。
- 控制台没有致命错误。

### 候选版本验收

用于内部构建：

- 安装包或便携包能够运行。
- 核心流程能够完成。
- 存档能够写入和读取。
- 关键 UI 没有阻断操作的问题。
- 已知问题已经记录。
- 构建可以追溯到需求、PR 和测试结果。

## 首批核心回归场景

项目接管后优先建立：

- 启动游戏并进入主界面。
- 创建新游戏。
- 完成一次核心回合。
- [RED-127 Windows 双人 WS 联机候选验收](RED-127-windows-ws-multiplayer.md)
- 获取和消耗关键资源。
- 执行一张牌或一次策略操作。
- 非法操作被拒绝，且状态没有损坏。
- 保存、退出、重新启动并读取。
- 相同种子和命令得到相同结果。
- Electron 应用可以启动和关闭。
- 发生失败时保存日志、状态、种子和截图。

## 游戏不变量

关键测试应逐步覆盖：

- 资源不能在规则不允许时变为负数。
- 同一个效果不能重复结算。
- 不存在或已失效的实体不能行动。
- 非法命令不能污染游戏状态。
- 回合和阶段不能进入无效组合。
- 同一初始状态、种子和命令序列应产生相同结果。
- 保存并读取后关键状态保持一致。

## 测试证据

PR 中根据风险提供以下证据：

- 自动测试报告。
- 手动测试步骤和结果。
- 状态快照或状态差异。
- 随机种子和命令序列。
- 错误日志。
- 截图或录屏。
- 构建包或运行记录。

没有自动测试时，必须明确说明，并提供可重复的手动验证步骤。不得将“没有执行测试”描述为“测试通过”。

## 不稳定测试

如果测试存在偶发失败：

1. 创建明确的修复任务。
2. 记录失败频率和已知条件。
3. 必要时暂时隔离测试。
4. 保留失败日志和随机种子。
5. 不得通过反复重试长期掩盖问题。

## 快照规则

- 快照变化必须人工检查。
- 不得为了让测试通过而自动覆盖快照。
- 快照应排除时间戳、临时 ID 和无关顺序等噪声。
- 关键状态应优先使用语义断言，而不是依赖完整文本或像素完全一致。

## 人工体验验收

自动测试不能代替以下判断：

- UI 是否易于理解。
- 操作反馈是否清晰。
- 游戏节奏是否合理。
- 视觉层级是否混乱。
- 数值体验是否有趣。
- 玩家是否知道下一步该做什么。

人工验收者可以与开发者是同一个人，但必须依据验收标准实际运行和检查，不能仅根据代码判断完成。

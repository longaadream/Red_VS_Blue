# 首次联机试玩：玩家与组织者指南

本版是 Windows x64 测试候选。玩家主机运行游戏权威与私有 PostgreSQL；公网服务仅负责目录、邀请码、HTTP / WebSocket 转发。1v1 与 2v2 共用这条联机链路。

## 玩家：从下载到开局

1. 下载组织者提供的同一版本 Windows ZIP，完整解压，再运行文件夹内的 `RED vs BLUE.exe`。不要直接在压缩软件里运行，也不要只复制 EXE。
2. 首次启动等待本机服务就绪，创建游客昵称。无需另装 Node、数据库或编辑环境变量。游戏数据保存在客户端自己的用户目录，不在解压目录。
3. 局域网：一人开启主机，其他人连接这台电脑的局域网地址。公网：进入“公网联机”，填组织者提供的 HTTPS 转发地址。
4. 当主机：填主机名称及组织者给你的发布密钥，点击“发布主机”，再进入本机大厅创建房间。复制邀请信息发给朋友。主机电脑需要保持开机且游戏不退出。
5. 加入：填写相同转发地址和 8 位主机邀请码，或从公开主机列表进入。进入主机大厅后加入其房间，选择阵营和阵容。主机邀请码与房间私密邀请码是不同层级。
6. 1v1 满两人，2v2 满四人才开局。2v2 使用 24×20 双翼战场，蓝1 → 红1 → 红2 → 蓝2；第四席获得幸运币。资源、操作和私密手牌各自独立。两位队友的场上核心全部消灭才判全队失败；投降需要两名队友同意。
7. 短时网络中断自动重连。120 秒后掉线席位由主机 AI 接管，重新加入后收回控制。不要通过换昵称/新建身份尝试找回旧席位，必须使用原身份。

主机程序退出或公网入口中断会影响连接；首版没有无缝主机迁移。主机恢复后需要重新发布，新的主机邀请码需重新分享。已有主机数据库保留，不要为排查连接问题删除它。

## 方案 A0：frp 只有公网 IP＋端口，没有域名或证书

可以使用 Windows 客户端已有的 HTTP / WebSocket 直连，不需要 TLS 证书。它不提供传输加密，先限熟人小批量测试；公共目录／主机邀请码入口仍要求 HTTPS。frp 自身隧道加密不等于玩家到公网入口这一段有 TLS。

1. 主机启动游戏，在“公网联机 → 我来当主机 → 查看 frp 本地目标”读取实际游戏端口。不要猜测固定端口，端口占用时程序可能改用其他端口。
2. 第三方 frp 面板选择 **TCP**，本地 IP 填 `127.0.0.1`，本地端口填上一步显示的数字。frpc 与游戏运行在同一台电脑。只映射这个游戏端口；不要映射数据库、资源管理或调试端口。
3. 主机点击“进入本机大厅建房”，把第三方分配的公网 IP＋端口发给朋友。无需点“发布主机”，无需填发布密钥。
4. 朋友打开“公网联机 → 直接连接主机”，填写 `http://公网IP:端口`，进入大厅加入房间。不要填入上方的“转发服务器地址”。此路径不使用公共主机邀请码，私密房间仍使用房间自己的邀请码。
5. 重启游戏后再次核对 frp 本地端口。主机与 frpc 都须保持在线；测试连接数和空闲断线策略由第三方入口决定。

这条路径的客户端明文 HTTP 和 SDK 连接能力已具备；当前第三方 frp 的实际可达性、长连接和容量尚未验证，先让一位异地朋友完成加入、开局及断网重连。

## 方案 A1：有 HTTPS 入口的内网穿透

不必先买云服务器。可以在一台保持在线的 Windows / Linux 电脑运行本包的 `multiplayer-relay`，用现有 frp 或穿透服务暴露它。

穿透入口需要满足：公网 HTTPS、有可信证书、HTTP 与 WebSocket 共用同一个域名、支持 `Upgrade`，并允许长连接。将入口转发至运行 relay 那台电脑的 `127.0.0.1:8080`。**暴露的是 relay 端口，数据库和客户端管理服务不需要穿透。**

在 `multiplayer-relay` 目录安装 Node.js 24 后执行：

```powershell
npm.cmd ci --omit=dev --ignore-scripts
$env:HOST = '127.0.0.1'
$env:PORT = '8080'
$env:RVB_RELAY_PUBLIC_ORIGIN = 'https://替换为你的穿透域名'
$env:RVB_RELAY_PUBLISH_KEY = '替换为组织者生成的随机发布密钥'
node start.mjs
```

玩家主机和加入者都填这个 HTTPS 域名。不要填 localhost。没有域名时可先用 `http://127.0.0.1:8080` 在同机做功能检查；该地址无法让异地朋友加入。

frp 的 HTTP / HTTPS 代理按域名转发，入口 TLS 和 WebSocket 能力需按实际提供商配置验证：[frp 官方说明](https://gofrp.org/en/docs/features/http-https/)。frp 不会自动附带可信证书，`https2http` 插件也需要自行提供证书文件：[HTTPS 配置示例](https://gofrp.org/en/docs/examples/https2http/)。免费或共享穿透的连接数、流量与空闲超时需要先确认，不能由本地压力结果推断。

## 方案 B：租服务器部署独立转发入口

服务包附 `deploy/multiplayer-relay/compose.yaml` 和 `Caddyfile`。目标环境为 Linux + Docker Compose；使用主机网络，relay 仅监听 loopback，Caddy 对外提供 HTTPS。Caddy 支持 WebSocket 转发：[官方文档](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)。

准备一台主机、指向其地址的域名、可用的 80/443 端口。初次小批量可从 2 核 / 2 GB 内存的转发节点验证，实际是否足够以本轮网络指标为准；优先看稳定带宽、丢包与跨运营商延迟。该配置是工程起点，不是已验证的中国公网容量承诺。客户端电脑仍承担对局计算。

```sh
cd deploy/multiplayer-relay
cp .env.example .env
# 编辑 .env：域名 + 自己生成的随机发布密钥，不要使用示例值。
docker compose up -d --build
docker compose ps
docker compose logs --tail=100 relay
curl --fail https://你的域名/healthz
```

默认最多 50 个发布主机、120 条游戏转发连接，每个主机 32 条；HTTP 临时请求也计入连接预算，适配不到 100 人的首轮测试。`/healthz` 输出当前主机/连接数、容量、运行时长及拒绝计数。日志只记录主机发布/断开生命周期，不记录身份私钥、发布密钥或对局数据。

仅信任 compose 中明确列出的本机代理 IP；Caddy 覆盖 `X-Real-IP`。如换成其他代理，不要直接信任互联网传来的客户端 IP 请求头。

停止服务：`docker compose down`。这会断开所有通过此入口连接的玩家，应在测试群宣布停服后执行。升级前停止接收新测试批次，等现有对局结束；保留原 ZIP 与 compose 文件，失败时恢复原候选并重新启动。relay 不存对局数据库；不要删除玩家主机的数据库来回退 relay。

## 第一轮批量测试安排

先由组织者和 3 名测试者用真实公网完成安装、创建/加入、至少一局、断网重连、主机重启和反馈收集，再扩大邀请。

| 批次 | 人数 | 放行要求 |
| --- | --- | --- |
| 冒烟 | 4 | 四台 Windows 使用同包，安装与两个入口可用；版本错误能阻止加入 |
| 小批量 | 12–20 | 至少 30 分钟；不同网络/运营商；断网后回到原席位；日志可定位失败 |
| 扩大 | 40–60 | 至少 60 分钟；多主机多对局；目录、加入、回合和重连成功率稳定 |
| 目标档 | 80–100 | 前两档无阻塞；至少 60 分钟，记录峰值连接、入口带宽、P95 延迟和异常退出 |

建议记录：下载/启动成功率、主机发布成功率、加入成功率、首次可操作耗时、断线次数、重连成功率、对局结束率、版本不兼容次数和影响人数。出现存档损坏、重复结算、跨玩家控制或连续多人无法加入，暂停扩大并保留现场。

首次发放只分享一个候选版本和一份 SHA256 校验文件。发现问题后发新候选 ZIP，暂不做静默强制更新。测试中不要混用不同资源包。

## 反馈模板

在“公网联机 → 连接检查与反馈”生成并复制诊断信息，再补充：

```text
候选版本：
发生时间（北京时间）：
网络：省份/运营商，宽带或手机热点（无需详细地址）
角色：主机 / 加入者；直连 / 公网转发 / 内网穿透
房间码、对局模式：
从哪一步开始出错：
期望发生什么、实际发生什么：
能否重现及步骤：
截图或战报：
诊断信息：
```

无需提供身份私钥、助记词、发布密钥或完整数据库。诊断通过玩家主动复制提交，不会自动上传。战斗内遇到问题先保留现有日志/战报，再退出。

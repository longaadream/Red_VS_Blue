# 同图冒险：存档与联机实施方案

状态：用户已于 2026-09-10 回复“可以”，批准本方案实施；实施中，尚未验收。关联 RED-181。

## 目标与既定规则

把当前三幕探索接入存档及 1–4 人合作。复用现有棋盘、原生技能与 Colyseus 连接，单人和联机共享冒险规则。每人自己的队长、预备队、货币、卡牌、遗物及成长；每轮玩家顺序随机并展示，全部玩家行动完后敌方统一行动。探索每人固定 3 AP；遭遇从 1 AP 逐轮递增，援军继承遭遇轮次并获得一个敌方阶段的保护。进入战区的玩家受封锁，区外玩家可继续探索或进入支援。

房主保存。缺席队伍不参加后续战斗；节点结算后允许回归或新人接管。接管沿用席位的队伍与账本，不能重复领取新人奖励。有限补偿仅补错过结算的基础金币，按内容配置上限及节点奖励 ID 记账，不复制掉落或成长。

## 现状与接入边界

- `lib/pve/roguelike/session.ts` 使用固定 HUMAN、单一 WorldProgress 和活动战区；其 snapshot 是玩家公开视图，删除了部分运行数据，不能当成存档。
- `lib/game/adventure-boundary.ts` 的 party、activeZone、AP 和越界判断同样只支持一个玩家。直接增加连接会把盟友误判为敌人，必须先改规则模型。
- `lib/pve/run-store.ts` 服务旧节点式 PVE。新增探索存档使用独立格式与目录，保留旧服务、旧文件及解析语义。
- `ADR-0027` 已规定 Colyseus 单会话重连、房间命令队列、权威回执与 PostgreSQL 耐久层。冒险房间复用这些基础设施，不新增浏览器间自制同步或第二套客户端权威。

## 实施结构

### 1. 可序列化的冒险会话

将全局内容、地图、幕数、随机游标及世界轮次归入 run；将 coins、recruited、upgrades、reserves、captain、hand/relic/growth 和个人领取记录按 playerId 存储。每个遭遇记录参战者、固定敌方阵容、轮次、预告、奖励状态及边界，玩家最多加入一个活动遭遇。

命令显式携带 actor，由宿主绑定的席位身份校验；snapshot(viewerId) 只暴露接收者有权获取的数据和合法操作。单人作为一席同一路径运行。各场遭遇共享世界轮次，敌方阶段统一调度已发布行动，不因某个客户端催促而提前或重复推进。使用既有注入种子生成随机玩家顺序，保存游标，不更换核心 RNG。

原生引擎仍独占移动、技能、伤害与终局计算。新增 PVE 模式限定的团队及遭遇判断，禁止波及未激活敌人，禁止越界支援技能绕过封锁。玩家队长阵亡不立刻结束整局，所有仍参与冒险的队伍失去战斗资格时才判负；胜利后按已确认规则复活队长至 1 HP。

### 2. 独立版本存档

新增 `rvb-adventure-checkpoint/v1`，包含完整权威 BattleState、run/玩家/遭遇元数据、当前生成地图及内容引用、初始恢复基线、招募候选、奖励去重账本、revision、随机状态和 Profile 身份。Profile 身份沿用 engineAbi、runnerRevision、resolvedProfileHash、authorityContentHash。

节点结算或幕切换完成后请求自动存档；多战区下若另一场仍在战斗，只标记待保存。全世界无活动遭遇、无目标/奖励/溢出选择、无敌方执行中的稳定探索边界才实际保存，手动保存使用相同条件。战斗中显示“上次已保存”的时间和幕数，不伪称当前进度已保存。房主可读取最近节点档并重新开房。

写入先校验完整性再原子替换，保留上一份可用档；写入失败不覆盖旧档。读档先在隔离对象中校验格式、状态结构、不变量和资源身份，成功后才替换会话；技能定义只从匹配的可信 Profile 重新绑定，不执行存档内附带脚本，不在读取时重跑开局、重抽奖励或重新生成地图。旧节点 PVE 档给出明确不兼容提示，不静默转换。

房主指房间的管理席位；真正的写盘操作由权威宿主执行，客户端不能直接提交金币、胜负或任意 BattleState。单人桌面与 Host & Play 使用本机权威服务；普通浏览器预览要接入同一 QA 权威服务，不能用 localStorage 冒充正式耐久存档。

现有 PostgreSQL journal 的记录类型只覆盖 BattleAuthorityTransitionRecord，需新增冒险 aggregate 的类型与仓储适配。整个 run、BattleState、个人账本及幕切换共享 revision/hash 和原子耐久提交，不能只保存战斗 hash 或另起非事务金币文件。仅在确认 durable 水位达到该 revision 后显示“已保存”。

### 3. 合作房间与恢复

新增独立 AdventureRoom，复用既有身份、房间邀请码、内容匹配、FIFO、动作 ID 回执及 SDK 原生重连。上限四席；先完成资源身份校验再进入准备界面。资源不一致时阻止开始并列出差异；已有可信资源包安装入口负责匹配，下载失败不能放宽校验。

断线立即禁用该客户端输入，重连恢复原席位、revision、手牌和预告，不新建替代会话。战斗中不即时删除缺席棋子或减少敌人阵容；断线宽限期后按显式缺席规则跳过该玩家的普通行动，涉及未完成目标选择必须经过引擎合法取消或既有超时处理，不能卡住全队。全世界稳定的节点结算边界才暂停其队伍或进行接管，不因另一战区结算而删除还在战斗的棋子。新人接管须房主明确选择并废止原席位旧凭据，旧连接不能再次取得该队伍控制权。

首版不做房主进程迁移。房主仅关闭客户端、权威服务仍运行时，其他玩家可继续；本机权威服务关闭时所有客户端提示连接中断，房主重启后从最近存档恢复。云端服务器部署仍沿用现有服务配置，本方案不授权发布服务或开放公网端口。

### 4. 页面

冒险入口增加“创建冒险”“加入冒险”“继续存档”。准备页显示四席、各自队伍、资源匹配状态和房主开始按钮。局内增加队友头像/连接状态、当前轮序、自己的资源、保存状态与房间菜单；保留当前木桌、纸页、动漫头像及棋盘渲染。每个战区独立显示轮次和预告，不占用日志位置。

## 实施顺序与验收

1. 拆出按玩家/遭遇组织的权威状态和命令，先跑单人回归及 2/4 人无网络固定种子模拟。显式验证四名玩家加敌方阵营的 AP、盟友判断与终局；一边战区结算不能清理另一边的预备队、状态、伤势或 AP；援军同世界轮不能多获得一次玩家回合。
2. 实现 checkpoint/store：存取前后状态 hash、地图、候选、伤势、牌成长及后续相同命令结果一致；覆盖坏档、错版本、资源不匹配、写入失败及重复领奖。
3. 接入 AdventureRoom：真实双 SDK 客户端与四客户端走移动、部署、目标选择、奖励、跨幕；验证越权、过期 revision、同动作重复请求、连接丢失后的回执查询。
4. 实现页面并实测双窗口：各自控制队伍，多战区互不污染；晚加入 AP 和保护正确；一个玩家阵亡队友继续；房主存档、退出、重开、队友重连后状态一致。
5. 类型/lint/build、PVE 全套及 PvP/team/deployment/Colyseus 相邻测试，独立 AI 审查；保留日志与可复现种子。以上未全部完成前不宣称联机可用。

# 技术文档

状态：草案  
负责人：项目负责人  
适用版本：重构版本

本目录用于记录 Red VS Blue 的系统架构、模块边界、公共接口、游戏引擎、存档设计、测试入口和调试方法。

当前最重要的技术目标是：让问题能够稳定复现、快速定位和可靠验证。

## 技术目标

项目逐步达到以下状态：

- 游戏规则与 React/Electron 界面解耦。
- 核心规则可以在不启动完整界面的情况下运行。
- 玩家操作可以记录、重放和逐步检查。
- 随机行为可以通过固定种子复现。
- 游戏状态可以稳定序列化和比较。
- 错误报告包含操作、状态、日志、截图和随机种子。
- 每个主要模块都有明确入口、出口和负责人。
- AI 只需读取相关模块文档，不需要扫描整个项目。

## 目标架构边界

### 游戏规则层

负责：

- 回合与阶段推进。
- 卡牌和策略效果。
- 资源变化。
- 实体状态变化。
- 合法性检查。
- 胜负判断。

不负责：

- React 组件渲染。
- Electron 窗口操作。
- 直接读取系统文件。
- 播放动画或声音。

### 表现层

负责：

- 页面和组件。
- 玩家输入。
- 状态展示。
- 动画、音效和视觉反馈。

表现层只能调用规则层提供的命令和查询接口，不得复制核心规则。

### Electron 系统层

负责：

- 桌面窗口。
- 主进程与渲染进程通信。
- 文件系统和系统能力。
- 应用启动、关闭与更新。

### 持久化层

负责：

- 设置保存。
- 游戏存档。
- 存档版本。
- 数据迁移。
- 读取失败与恢复处理。

### 数据层

负责：

- 卡牌配置。
- 事件配置。
- 数值表。
- 静态文本和内容数据。

## 公共接口原则

- 公共类型集中定义，禁止不同模块复制相似类型。
- UI 通过命令调用游戏规则，不能直接修改规则状态。
- 命令执行应返回明确结果，不使用无法判断成功与否的隐式行为。
- 错误结果应包含稳定的错误代码和可读说明。
- 外部系统能力通过适配器接口注入。
- 接口发生不兼容变化时，必须更新文档和相关测试。
- 未经批准不得创建新的全局状态来源。

建议的命令结果结构：

```ts
type CommandResult<T = void> =
  | {
      ok: true;
      value: T;
      events: GameEvent[];
    }
  | {
      ok: false;
      errorCode: string;
      message: string;
      context?: Record<string, unknown>;
    };
```

## 调试信息最低要求

一次可用的问题报告应尽量包含：

- 使用的游戏版本或提交编号。
- 初始场景或存档。
- 当前回合和阶段。
- 当前执行者。
- 随机种子。
- 玩家操作或命令序列。
- 预期结果。
- 实际结果。
- 错误日志。
- 失败前后的关键状态。
- 截图或录屏。
- 是否可以稳定复现。

只有错误文本、没有操作和状态上下文的日志，不视为合格调试证据。

## 测试控制接口目标

后续逐步实现统一的测试控制接口：

```ts
interface GameTestHarness {
  reset(seed: string, fixture?: string): Promise<void>;
  dispatch(command: GameCommand): Promise<void>;
  advanceTime(milliseconds: number): Promise<void>;
  getState(): Promise<SerializableGameState>;
  captureScreenshot(name: string): Promise<string>;
  exportTrace(): Promise<GameTrace>;
}
```

该接口是目标设计。接管最新代码后，应先评估现有架构，再决定如何分阶段实现，不能直接进行未经验证的大规模重构。

## 文档状态

- 草案：目标设计或初步整理，尚未验证。
- 待验证：来自旧代码或旧文档，需要与最新项目核对。
- 有效：已经与当前代码核对，并由项目负责人确认。
- 已废弃：不再适用，仅保留历史参考。

## 最新代码接管后的第一轮工作

拿到最新项目后，优先完成：

1. 确认实际安装、启动、测试和打包命令。
2. 生成项目目录和模块清单。
3. 找到游戏状态的唯一来源。
4. 找到玩家操作进入规则系统的入口。
5. 找到回合、卡牌、资源和胜负判断的实现位置。
6. 找到随机数、时间、存档和 Electron 通信入口。
7. 记录核心流程调用链。
8. 列出重复规则、跨层依赖和隐藏状态修改。
9. 建立最小可运行基线。
10. 选择一个高频问题建立首个可重复调试场景。

在完成代码核对前，旧版本资料只能标记为“待验证”，不能直接当作重构版本的最终技术规范。

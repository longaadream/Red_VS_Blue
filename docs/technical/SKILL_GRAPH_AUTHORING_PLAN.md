# 技能描述与可视化流程图编程接入方案

状态：长期接入路线。主动技能的 Schema、受限编译器和节点画布首版已实现，准确的已支持节点、操作步骤与限制见[首版手册](SKILL_GRAPH_V1.md)。本文中的事件入口、跨回合配方、集合与逐步回放仍是后续阶段，不能据此认为已经全部可执行。首要依据为[语言标准](../product/SKILL_DESCRIPTION_STANDARD.md)、[规则词典](../product/RULE_DICTIONARY.md)、[现役作者手册](SKILLCODE_AUTHORING_STANDARD.md)和[规则生命周期](RULE_LIFECYCLE.md)。

## 1. 当前基础与目标

[PR #161](https://github.com/longaadream/Red_VS_Blue/pull/161)统一状态、计时、伤害结果和部分位置变更入口；[PR #162](https://github.com/longaadream/Red_VS_Blue/pull/162)提供技能、关键词、状态和规则关联的可视化字段编辑。核对版本分别为 `90af9ccc70440ecd291c8316b22bfa9e13131810`、`19f9e568e315fb375d23cc566df35fd74e42f56f`，基线 `e9b6918080010f30f5b2fe5f535548f80c90a257`。当前实现已在独立集成分支合入 PR161 的 5a8bf3669dbd764c0e15370d76b5f22ec74bbb95 和 PR162 的上述版本，未合并 main。

PR #162 的标签编辑尚不决定实际效果；工作台检查和场景记录不等于运行战斗。RED-192 的状态定义也还不是完整可执行节点目录：关联规则的安装、不同脚本入口的能力与生命周期仍需显式适配。

建议以一份结构化技能定义作为新内容的作者来源，产出流程图、参数、描述和运行时调用。自然语言用于设计和审核；自由文本不能直接作为权威执行程序。旧 SkillCode 在完成逐项迁移前仍由原代码执行，不宣称能自动从任意 JavaScript 还原流程图。

## 2. 定义中的组成部分

| 组成 | 必须保存的信息 | 对应语言 |
| --- | --- | --- |
| 入口 | 主动使用／事件响应／开局授予；所属棋子或玩家；事件阶段 | 使用时、你的回合开始时、棋子死亡后 |
| 选择器 | 手动或自动、对象类型、数量、敌我、是否含本棋子、范围中心、距离算法、过滤条件 | 本棋子7格内1个其他友方棋子 |
| 条件 | 有类型的比较及真假分支 | 若准备进度归零 |
| 数值表达式 | 固定数值、属性读取、事件结果、百分比、逐步取整 | 本棋子攻击力250%、实际伤害50% |
| 效果 | 稳定能力ID、参数、顺序或获准批次、返回结果 | 造成伤害、恢复生命、传送 |
| 持续规则 | 持有者、状态类型、持续时长／结束条件、来源、绑定规则 | 获得定身，持续1回合 |
| 状态内进度 | 保存位置、初始值、更新事件、完成条件、完成后移除或标记 | 准备进度6；开始时推进；归零完成 |
| 使用约束 | AP、CP、冷却、每局次数等已有结构字段 | 参数栏及尚需保留的正文限制 |
| 显示信息 | 名称、现有关键词引用、说明模板、可选风格文字 | “万花筒。”与角色名称 |

同一项数值只保存一次，由描述、预览和图节点引用。中文名允许改，稳定ID不随显示名改变。标签使用显示映射；`effectTags` 是分类，技能 `statusTag` 是关联配置，战斗 `statusTags` 是实例，不能混为可执行能力。

## 3. 节点目录与端口

每种节点至少声明：`id`、`version`、中文名、参数 Schema、输入输出类型、允许入口、是否修改状态／请求玩家选择、运行时适配器、描述模板、验证场景。这里的字段名是方案，不是当前已存在的 API。

首批类型至少区分：`PlayerRef`、`PieceRef`、`Cell`、`PieceSet`、`DamageSource`、`DamageResult`、`StatusRef`、整数、布尔值、伤害类型、持续时间及阶段。一个能读取但已死亡的来源引用，不等于一个能接收棋盘效果的存活目标；目标有效性由对应能力检查。

典型检查：

- 传送要求棋子与地格，不能接玩家或伤害数值。
- 反冻要求敌方棋子来源。`DamageSource` 为玩家或环境时，必须走没有棋子目标的分支。
- 吸血引用 `actualDamage`；预估或结算伤害不得默认接到“实际伤害”端口。
- 持续时间携带持有者计时规则，进度携带开始／结束事件，二者不能用同一个数字端口代替。
- 一个效果必须有明确的控制流前驱；数据连线本身不表示执行。使用效果输出的节点必须位于该效果之后，分支输出只能在其有效路径内读取。
- 首版图内不开放任意回边。重复触发通过事件与持久状态表达；集合遍历、随机选择和批次使用有界、确定性的专用能力。

事件订阅优先级继续遵守 [ADR-0006](../decisions/ADR-0006-combat-trigger-ordering.md)及其后续取代条款，不能用画布上的上下位置决定。只有伤害、治疗、召唤、死亡使用 [ADR-0022](../decisions/ADR-0022-deterministic-effect-batch-queues.md)允许的批次，其他效果保持显式顺序。

## 4. 公共能力复用与当前缺口

| 作者节点 | 现有基础 | 接入时必须补齐 |
| --- | --- | --- |
| 造成伤害／治疗 | 公共伤害与治疗管线、实际伤害结果、事件队列 | 根动作与触发回调使用不同适配器；响应中使用获准 writer，不重入同步 facade |
| 获得／移除状态 | `status-lifecycle.ts` 的合并、计时、来源清理 | 完整状态配方应安装状态及其必要规则；现役 `addStatusEffectById` 本身不能被当作全部安装行为 |
| 传送／冲刺／推拉／换位 | `position-change.ts`、`context.changePositions` 及已有传送 helper | 各入口能力并不相同；冲刺还要携带路径与碰撞配方，不能只改终点坐标 |
| 回合开始／结束 | `turn.ts` 阶段检查点 | 对应明确的用户侧开始效果阶段；不得把部署前刷新与部署后开始效果合成一个模糊事件 |
| 死亡／复活／离场 | 已有伤害生命周期、复活与离场行为 | 三者分别适配；首版不开放任意处死节点，死亡批次也不自动变成作者可调用能力 |
| 获得玩家资源／卡牌 | 已有玩家规则和资源／手牌处理 | 保留玩家来源、资源上限和满手等现有规则；不能借棋子对象充当玩家 |
| 选择目标 | `targeting.steps`、权威 pending 与根动作重放 | 图的选择顺序必须生成同一份声明；取消、重试、重连不会重复提交费用或效果 |

位移和状态共用入口提供了基础，尚不能声称所有旧脚本已经通过新节点执行。技能、卡牌、规则、触发回调和 pending 的能力不同；节点目录须按执行入口限制可选项。

## 5. 三个可核对的图例

下列箭头表示拟议节点的执行和数据依赖，不是新增的运行时代码。

### 收割：结果驱动的被动

```text
本棋子造成实际伤害后
  → 读取本次事件的 actualDamage
  → 乘以 50%，向下取整
  → 将治疗请求加入获准的治疗队列：目标=本棋子
```

事件已包含一次伤害结果，不能再加一个“造成伤害”节点使原伤害重复。目标剩2生命、结算10点伤害时，实际伤害2，治疗请求1；治疗最终能否恢复生命仍由治疗管线决定。参考 [reap](../../data/skills/reap.json)、[伤害管线](DAMAGE_PIPELINE.md)。

### 神威·转移：多步选择

```text
主动使用
  → 选择本棋子7格内1个其他友方棋子
  → 选择本棋子7格内1个空的可行走地格
  → 传送：棋子=选定友军，落点=选定地格
```

两个范围中心都是施法棋子。取消第二次选择不应留下第一次选择产生的战局修改；实际提交重验禁锢、地形、占用和预留等现有公共约束。参考 [obito-ally-teleport](../../data/skills/obito-ally-teleport.json)。

### 仙人模式：跨回合的状态配方

```text
入口A：主动使用 → 获得打坐状态（准备进度=6，关联行动限制与开始效果）

入口B：该状态持有者所属玩家的回合开始效果阶段
  → 统计存活的友方影分身
  → 准备进度减少 1+分身数
  → 若进度归零：结束打坐 → 该玩家获得3行动点、1充能
```

进度保存在权威状态中，不用“等待6回合”节点、闭包、浏览器计时器或本地变量跨回合等待。完成后的状态清理及阶段检查点保证奖励仅提交一次。参考 [仙人模式](../../data/skills/naruto-sage-mode.json)、[规则生命周期](RULE_LIFECYCLE.md)。

## 6. 迁移路径与验收门槛

### 阶段一：在 PR #162 的字段编辑基础上增加描述助手

选取已核对的小组技能建立结构化定义样例。先提供“触发时机—目标—效果—持续时间”表单和生成描述预览；显示新旧差异，未确认不覆盖旧正文。表单与后续节点画布编辑同一份结构数据。

此阶段只作作者辅助，旧代码仍负责执行；明确显示“描述已检查”和“战斗已验证”的区别。先支持收割、神威·转移、圣盾／定身类状态；仙人模式用于验证结构能否表达跨回合状态，待相应适配器完成后才开放执行。

验收：文案保留目标、数值、时机和限用；范围中心不可丢失；未知旧字段继续保留；未支持效果明确标注，不能生成伪完整的技能。

### 阶段二：建立最小可执行闭环

为已批准能力建立有版本的结构定义及适配器，受信任的官方内容先试点。图定义生成目标步骤、描述与对公共运行时能力的调用。逐个技能比较原执行与新执行的合法动作、状态差异、事件、费用、随机消耗和 pending 结果。

验收至少包含：

- 收割：实际扣血、过量伤害、完全抵挡、治疗限制。
- 状态：圣盾唯一、定身计时与时长叠加、不同来源的撤销。
- 传送：两次选择、取消、重复提交、禁锢、占用与预留格。
- 确定性：同状态、种子、输入产生相同结果；非法图或输入不污染状态。

一项技能在一个版本中只启用一种权威执行模式，禁止旧代码与图效果都执行。迁移覆盖率按已验证技能记录；不以画布支持多少种方框代替。

### 阶段三：加入画布、组合配方与逐步回放

让作者拖动同一结构的节点，并逐步回放一次技能：当前节点、选择答案、伤害结果、状态变化、触发来源。节点ID映射到现有事件与 trace，不另建一套独立战局状态。

将“造成伤害后治疗本棋子”“附加限时控制”“玩家回合开始推进进度”等常用组合保存为有版本的配方。配方调用基础节点；特殊角色只填写差异。复杂角色保留未迁移脚本入口，不要求把任意代码强行转换成节点。

## 7. 版本、冲突与回退

后续正式实现须给 Schema、能力目录及生成器独立版本，记录来源技能ID和节点到生成产物的映射；任何规则语义变化纳入现有规则版本与内容身份检查。当前文档不新增存档格式。

已迁移技能的结构定义是其作者来源，生成描述和目标参数不再独立修改；自定义风格文字只能放在不改变语义的展示区。人工改了旧代码或生成字段时，工具应提示偏离与重新验证，不默默覆盖，也不继续声称图与代码一致。

原子写盘及内容冲突检测沿用 PR #162；权威操作提交和 pending 重放沿用现有 BattleRunner。受限运行能力遵守 [ABI v1](SKILLCODE_ABI_V1.md)和[威胁模型](SKILLCODE_THREAT_MODEL.md)，不因图形化就放宽外部可执行内容的准入。

每个试点保留可回退的独立提交及原执行模式。回退节点实现不意味着可以无损恢复正在执行新规则的旧对局。正式跨模块实施需另行给出具体文件范围、方案、测试与回退合同；当前首版具体实现与验收记录见首版手册和 QA；后续事件适配、配方及战斗逐步回放需扩展相应合同与测试。

# ADR-0022：开局双随机先锋、渐进式预备区部署与部署当回合免费首移

- 状态：已接受（实现等待 RED-138 验收）
- 日期：2026-08-31
- 人工批准：2026-08-31
- 关联任务：RED-138
- 风险：High
- 取代范围：新建对局的部署规则取代 ADR-0001、ADR-0007、ADR-0009，以及 ADR-0014 和 ADR-0019 中依赖初始 16 枚全图部署、公开重投与独立部署计时的条款；这些旧条款只继续服务 `legacy-reroll-v1` 和缺少 mode 的历史状态。

## 背景

旧规则在正式对局开始前就把双方 16 枚核心棋子全部放到棋盘，并立即要求玩家同时理解 8 枚己方棋子、8 枚敌方棋子、位置、状态和技能。前期只有 1–3 点行动点，移动又与技能共用行动点，因此最优选择通常把行动点均匀投入技能，主动移动直到约 4 费后才出现。实际对局常在 6–7 费结束，玩家既没有足够时间完成局面分析，也很难通过移动重新塑造初始站位，造成决策过密、棋子被迫放弃和掌控感不足。

本次目标是直接减少每回合需要同时处理的场上实体，并让每枚新棋子通过“落位 + 部署当回合第一次普通移动免费”形成可感知的棋类动作，而不是增加角色配对、额外资源或另一套复杂操作。免费首移通过棋子的公开 statusTag 融入正常行动，不新增必须立即处理或显式跳过的阶段。RED-138 同步为 AI Environment 增加渐进部署观察与合法动作接口，并让桌面实时 bot 用固定最小策略走通该流程；AI 表现、位置/角色估值、难度、胜率和策略强度仍不作为玩家体验或数值平衡参照。

## 决策

### 1. 模式、初始状态与兼容边界

- `BattleState.deployment.mode` 新增显式模式。新建正式对局默认使用 `progressive-reserve-v1`；显式 `legacy-reroll-v1` 和没有 mode 的历史状态继续走旧部署重投归约器。
- 渐进式对局先以空棋盘建立双方普通预备区。基尔加丹按第 5 节先移入仪式扩展；服务端随后按标准化 playerId 的稳定顺序，为每方从普通预备区确定性随机抽取 1 枚稳定核心实例，并确定性随机放到当时空闲、可行走的格子，作为该方开局先锋。
- 先锋抽取使用 `progressive-deployment/opening-piece/<normalizedPlayerId>`，先锋落位使用 `progressive-deployment/opening-cell/<normalizedPlayerId>`。两类流与双方玩家之间彼此独立，不推进候选、后备落位、技能、旧部署或对方的随机 cursor。普通预备区与空格都先按稳定顺序排列，每次抽取和落位各消费一次对应流随机值。
- 双方先锋依次经过正式 `beforePieceSummoned` → 稳定实例入场 → `afterPieceSummoned` 边界，但不获得部署免费首移 statusTag。核心终局检查在双先锋初始化期间暂停；只有稳定顺序中的两枚先锋及其触发队列全部结算后，才一次性跨过初始化屏障。不得在第一枚先锋完成而第二枚尚未召唤时判断后者核心全灭。
- 除双先锋外不生成其余初始坐标，也不消费旧 `deployment` 流的 16 次随机。
- 本决策不提升 `BATTLE_STATE_VERSION`，不迁移或原地改写进行中的 legacy 状态。模式字段和预备区均为 additive 状态；旧状态缺少 mode 时必须确定性解释为 legacy，不能猜测转换。
- ADR-0019 的受控四图目录、冻结 `Room.mapId`、开战前失败关闭和地图准入仍有效。其“16 次初始部署与重投保持不变”只适用于 legacy；渐进式落位按本 ADR 的全部空可行走格计算。

### 2. 每回合 seeded 三选一

- 双先锋初始化不替代第 1 回合部署。每个自己的回合在 `beginTurn` 等回合开始结算之前检查普通预备区；存在棋子时，服务端生成至多 3 枚互不重复的权威候选；预备区少于 3 枚时全部进入候选。没有普通预备棋子时跳过本阶段。
- 对 8 枚普通核心、无死亡的标准阵容，初始化后场上为 1 枚；自己的第 `t` 个回合部署完成后为 `N(t)=min(t+1,8)`。含基尔加丹的阵容遵守第 5 节仪式例外，不用该公式把仪式暂存实例视为普通预备核心。
- 候选池先按稳定 `instanceId` 排序，再执行仅覆盖候选槽位的 partial Fisher–Yates。第 `i` 个候选只消费一次随机值，因此每次候选恰好消费 `min(3, reserve.length)` 次。
- 候选使用 `progressive-deployment/offer/<normalizedPlayerId>` 命名流。不同玩家互不推进对方候选流，也不推进技能、旧部署或落位兜底流。
- 同一根 seed、地图、玩家、阵容和已接受动作序列必须产生相同候选、cursor 与状态。候选没有重投入口；非法或失败动作不会提交状态或额外随机消费。

### 3. 原子选棋与落位

- 候选选择和格子选择在客户端只作为本地交互状态；服务器只接受一条原子 `deployReservePiece` 命令，并同时验证当前输入玩家、回合、候选实例和权威落点。命令必须携带与当前状态精确相等的 `expectedDeploymentRevision`；缺失、非安全整数或过期 revision 在克隆、随机消费和任何状态修改之前以 `PROGRESSIVE_DEPLOYMENT_STALE_REVISION` 拒绝。成功时移动预备区中的同一稳定核心实例，失败时不能产生半部署状态。
- 安全落点为所有空的 `walkable === true` 格中，与每一枚存活且已放置的场上棋子曼哈顿距离都严格大于 5 的格子。格子按 `(y, x)` 稳定排序；没有存活场上棋子时，全部空可行走格都安全。
- 有安全落点时，命令必须提交其中一个精确坐标，服务端不接受客户端自行计算出的范围外坐标。
- 没有安全落点但仍有空可行走格时，客户端只提交候选棋子。服务端使用 `progressive-deployment/fallback/<normalizedPlayerId>` 流在按 `(y, x)` 排序的全部空可行走格中消费一次随机值并确定一个格子；结果不能重投。
- 如果连空可行走格也不存在，命令以稳定错误失败关闭，不移出预备区、不消耗落位随机、不修改 hash。
- 落位依次执行 `beforePieceSummoned`、重新校验触发器可能调整后的最终坐标、从预备区移出并加入棋盘、`afterPieceSummoned`。`beforePieceSummoned` 阻止或最终坐标非法时不提交召唤；若命令进入安全落点分支，调整后的坐标仍必须属于当次权威安全格集合，兜底分支则仍必须为空且可行走，否则以稳定错误回滚且不消费随机；`afterPieceSummoned` 的阻止语义继续遵守既有触发队列规则。
- before/after 触发器要求选项或目标时，复用既有可挂起动作事务：权威状态保持在根命令提交前，按同一随机检查点重放，直到当前消费者、后续规则与响应卡队列全部结算后才原子提交部署并授予本节定义的 statusTag。

### 4. 部署当回合免费首移 statusTag 与生命周期顺序

- 双方先锋在对局初始化中真实经过召唤边界；第一回合第一次 `beginPhase` 仍先且仅先结算一次 `gameStart`。仍留在渐进式预备区的棋子不会像 legacy 初始场上棋子那样被合成一次 `afterPieceSummoned`。
- 成功完成三选一部署后，只有刚刚进入棋盘且仍存活在场的稳定核心实例获得公开、可序列化的 statusTag：`id/type=deployment-first-move-free`、`name=本回合首次移动免费`、`grantedTurnNumber=<当前回合>`、`currentDuration=1`、`currentUses=1`、`visible=true`。开局先锋、技能召唤物、复活、变身、仪式召唤的基尔加丹及其他非三选一召唤均不获得。
- 标签只影响该棋子所属玩家在本回合提交的普通 `move`。第一次被权威接受并实际提交的普通移动继续使用权威直线、距离、地形、占位与触发规则，但消耗 0 行动点，并与移动提交原子消费标签；第二次及后续普通移动恢复既有费用。非法、过期、被拒绝或在 before-move 阶段阻止且没有实际提交的移动不消费标签或行动点；一旦实际提交，即使 after-move 效果把棋子移回原位、移出战场或改变位置，也不返还标签。
- 未使用标签必须在棋子被放置的这个当前回合结束、行动权交给下一玩家之前确定性移除。它不能转移、兑换行动点或跨回合保存；技能位移、强制位移、召唤落位和其他非普通移动既不享受也不消费。
- 不创建任何专用免费移动子状态或动作。总顺序冻结为：移出基尔加丹 → 按稳定玩家顺序完成双方随机先锋的 before/入场/after 触发队列 → 设置 `openingVanguardsInitialized` 屏障并检查终局 → 若未终局则结算首回合可选的 `gameStart` 完整触发队列并再次检查终局 → 若仍未终局才生成当前玩家候选 → 原子部署的 `beforePieceSummoned` → 实例入场 → `afterPieceSummoned` 完整触发队列 → 立即检查终局 → 若未终局则为本次部署核心授予 statusTag → 执行 `beginTurn`、冷却与其他既有回合开始结算 → 正常行动阶段。任何终局都必须在授予标签、下一次候选、回合推进或随机消费之前停止；玩家在部署流程完成前不能花费正常行动点执行其他动作。
- 渐进式部署没有独立 45 秒时钟。候选与落位由当前回合的同一权威成长计时覆盖；超时时服务端确定性选择第一个权威候选与第一个安全格，或按本 ADR 执行随机兜底，然后直接继续既有回合流程。玩家无需处理或跳过额外移动窗口。

### 5. 角色触发与首次语义

- 泰兰德和提里奥·弗丁的相关规则只响应“该规则所属棋子本人作为 `sourcePiece` 的 `afterPieceSummoned`”，并在每次实际召唤时结算；不再绑定 `gameStart`，也不在通用部署状态中记录首次。
- 任何确实只应结算一次的内容效果由该内容在 `battle.extensions` 中自行保存状态。本决策不增加通用 `firstSummoned`、`hasEnteredBoard` 或类似生命周期架构。
- 需要初始化预备区例外的棋子由模板字段 `progressiveDeployment.reserveInitializationSkillId` 数据驱动，核心部署层不得硬编码基尔加丹或技能 ID。基尔加丹的仪式规则把稳定实例按标准化 owner 存入 `battle.extensions.kiljaedanPiecesByPlayerId` 并发放首张仪式牌，因此同阵营镜像对局不会互相覆盖；单值 `kiljaedanPiece` 只保留为旧内容兼容指针，不作为新路径的唯一真源。该稳定实例不会进入三选一候选。
- 仪式召唤基尔加丹必须复用通用的 `beforePieceSummoned` → 稳定实例入场 → `afterPieceSummoned` 边界。它不是 `deployReservePiece`，因此不获得部署免费首移 statusTag。

### 6. 核心存活与终局

- ADR-0011 的 `terminalResult` 单一真源不变，但渐进式对局在双先锋初始化事务完成前以 `deployment.openingVanguardsInitialized` 设置明确屏障，不运行核心全灭判断。双方先锋与完整触发队列都完成后设置该字段并执行第一次检查；此后除既有公共动作边界外，还必须在部署 after-summon 队列之后立即检查，且检查先于授予免费首移标签、`beginTurn`、下一候选和任何下一步随机消费。普通移动仍使用既有动作完成后的终局边界。
- 初始化完成后，核心存活集合只包含“存活、已放置在场且 `isCore=true` 的棋子”。普通预备区、当前候选以及仪式暂存在 `battle.extensions` 中的基尔加丹都不计数，也不能阻止场上核心为 0 的一方败北；基尔加丹实际召唤至棋盘后，以保留的 `isCore: true` 身份重新计入。
- 若同一结算边界只有一方场上存活核心为 0，该方败北；若双方同时为 0，则沿用平局。普通召唤物仍不计核心，复活与变身仍保留原核心身份，强制移除记录、同时全灭优先级和终局只提交一次不变。

### 7. 公开投影、权威输入与传输边界

- 服务端状态保存完整普通预备区、候选和落点。公开投影始终移除预备区实例与规则函数，只公开每名玩家的预备区数量。
- 只有当前输入玩家收到本回合候选 ID/摘要与安全落点；对手、观战者和没有已验证 viewer 身份的请求收到空候选与空合法格。正式玩家的完整快照与重连恢复只通过已验证签名战斗身份的 WebSocket 订阅建立 owner 投影。Next Battle GET 只保留为内部兼容/测试处理器，实际玩家运行时的 `/api/rooms/**` 返回 410，不能作为恢复后备；内部直接调用 GET 时仍须验证签名才能建立 owner 投影，单独声明 `viewerPlayerId`、`x-player-id` 或同名字符串只按观战者处理。实际入场棋子及其 `visible=true` 的 statusTag 继续按普通战场可见性公开。
- 客户端只提交候选 ID、所需坐标与之后的普通 `move`，不在本地复制安全距离、随机兜底、召唤、移动扣费或标签消费规则。受支持的玩家传输入口、房间协调器与计时器调用同一权威动作入口。
- `aiEnvironmentV1` 与 `aiEnvironmentV2` 按请求中的 AI `playerId` 应用同一 owner 投影：公开
  `mode/status/revision/reserveCounts` 等阶段信息，只有当前输入玩家看到自己的 `offerPieces` 和
  `legalPositions`。对手 AI、其他 viewer 和无身份观察
  不能看到这些字段，也不能读取完整 `deployment.reserves`。
- AI 合法动作新增 `reserve-deployment` / `deployReservePiece`，并携带观察时的当前
  `expectedDeploymentRevision`；正式提交时重新校验，AI 不得构造、猜测或跨 revision 缓存凭证。
- 有安全格时，AI Environment 只枚举 offer 与权威 `legalPositions` 的组合；安全格为 0 但仍有空
  可行走格时，每个 offer 只产生不带坐标的动作，最终格仍由权威 seeded fallback 决定，不能被 AI
  预览或选择；无空格时返回无合法部署动作并保持失败关闭。
- Environment 保持只读/隔离。桌面 WebSocket 实时 bot 房改用 `progressive-reserve-v1`：部署时固定
  提交稳定排序后的第一个 `reserve-deployment`，部署完成后直接进入既有普通行动逻辑。带标签棋子的
  普通移动是否为 0 行动点完全由同一权威移动 reducer 表达；完整动作每次都重新提交房间 authority/CAS，
  不能把模拟状态写回房间。
- 上述固定策略只保证机器人可以确定性、可回放地经过新状态机，不新增位置估值、角色估值或难度调优，
  也不作为 RED-138 节奏、平衡、胜率或 AI 强度验收。
- RED-138 的受支持渐进传输范围是 Windows/Electron 权威房间 WebSocket。RED-117
  `lib/pve/battle-adapter.ts` 的 formal Run 继续显式 `legacy-reroll-v1`。Android 当前
  `action-log` 会把 init 日志交给客户端重放，不具备本节要求的签名 viewer 私有投影，因此
  `progressive-reserve-v1` 在 RED-81 完成前属于不受支持路径；Android 及其旧协议只继续解释
  legacy 状态，不得作为 RED-138 候选发布、跨端一致性或隐私验收证据。

### 8. Trace、回放与随机审计

- Action Trace 记录模式、`openingVanguardsInitialized`、revision、候选/部署动作、部署阶段、输入玩家、预备区数量、触发器调整后的实际 `deployedPosition`，以及候选流和兜底流的起止 cursor。检查点与普通移动动作状态差异必须覆盖免费首移 statusTag 的授予、消费和回合结束清除；挂起交互的恢复帧必须关联原始部署根命令并在真正提交后记录落点，失败或仍未提交的帧没有伪造落点，也不提交 cursor。
- Trace v2 继续保存记录状态而不是用当前规则重跑。初始化帧必须记录双先锋的稳定实例、最终坐标、玩家处理顺序、四条独立命名流及 cursor；检查点必须包含可恢复的预备区、部署状态和稳定核心实例。对外进行中投影仍按 ADR-0016 隐藏完整 trace 与回放。
- 本 ADR 只新增命名流用途，不修改 ADR-0004 的 FNV 派生、Mulberry32、cursor、逻辑时钟或 hash 算法。新增流不会推进任何既有流。

## 备选方案

- 保留 16 枚棋子全部初始上场，只延长回合时间：不采用；同时信息量和初始站位支配仍然存在，只会延长等待。
- 用“角色对”或额外编队层降低选择：不采用；会增加记忆、配置和操作复杂度，偏离让游戏变简单的目标。
- 每回合让 2–3 枚棋子移动或给移动返还行动点：不采用；仍要求从大量场上实体中先选角色，不能降低开局决策宽度。
- 所有新棋子都完全随机上场：不采用；仅开局双方各 1 枚先锋随机抽取并随机落位，用于生成简单且可复现的初始局面。此后的回合部署仍由玩家三选一并选择安全落点，只在没有安全落点时保留一次服务端随机。
- 部署消耗行动点：不采用；前期资源已经紧张，会继续迫使玩家在上场、移动与技能之间放弃棋子。
- 部署后新增独立免费移动/跳过阶段：不采用；会制造额外强制决策和状态机分支。公开 statusTag 让玩家在正常行动中自行决定是否以及何时使用当回合免费首移。
- 在通用棋子模型记录“首次上场”：不采用；当前首次效果可以在具体内容的 `battle.extensions` 内实现，没有必要扩大生命周期状态面。

## 影响与风险

- 收益：对局从双方各 1 枚先锋的可读局面开始，第 1 个自己的回合部署后才增长至 2 枚，场上实体此后逐回合增加；每次回合部署都有玩家可控落位，且新棋子可在正常行动中使用当回合免费首移，不增加一次必须处理的独立窗口。
- 成本：初始化新增双先锋召唤屏障，回合开始新增一个必须处理的部署输入；公共状态、计时器、场上核心终局、角色召唤、普通移动扣费、回合清理、回放、AI Environment 与桌面实时 bot 调度都必须理解新的标签生命周期。
- 主要风险：模式解释错误会让旧对局进入错误归约器；第一枚先锋后过早检查终局会误判第二方败北；误把预备区计作存活会延迟本应立即发生的终局；开局、候选或兜底随机消费漂移会破坏回放；候选投影或 AI observation 泄漏会暴露隐藏选择；免费首移的 AP 扣费与标签消费不原子或回合结束未清理会造成重复优惠；bot 缓存旧 revision 会产生拒绝或死循环；基尔加丹同时存在于普通预备区和 extension 会复制稳定核心实例。
- 本决策不调整 AP 成长、技能费用、伤害、治疗、技能冷却、地图目录或胜负回合上限。相关平衡必须依据真人测试另立任务。

## 验证方式

- 固定 seed 验证：基尔加丹先排除；按稳定玩家顺序为双方各抽取并随机落位 1 枚普通核心；位置为空且可行走、互不重叠；before/after 召唤完整发生但不获得免费首移 statusTag；四条独立开局命名流各精确消费一次，旧 `deployment` 流没有 16 次消费。
- 验证第一枚先锋及其触发完成后不结算终局，第二枚先锋与触发队列完成后才第一次检查；之后单方场上核心为 0 即败北，普通预备核心与隐藏基尔加丹均不能阻止，双方同一边界为 0 则平局。
- 验证双方第 1 个自己的回合仍有三选一；8 枚普通核心且无死亡时满足 `N(t)=min(t+1,8)`，并验证每次至多 3 个唯一候选、稳定 partial Fisher–Yates 与精确 cursor。
- 验证安全距离严格大于 5、全场存活棋子约束、稳定格子顺序、无安全格的一次确定性兜底，以及绝对无空格时状态/hash/cursor 不污染。
- 验证稳定实例从预备区原子移至棋盘、before/after 触发顺序、交互触发未完成时保持根命令前状态、完整队列和终局检查后直接进入正常行动，且只有该实例获得仅部署当前回合有效的公开 statusTag；不存在独立免费移动/跳过阶段。
- 验证第一次成功普通移动 AP 不变且原子消费标签，第二次按既有规则扣费；非法、过期、错误玩家和 before-move 阻止不消费，已提交后的 after-move 位移不返还；未使用标签在 endTurn 交接前清除，不能跨回合或转移。
- 验证候选和合法格只向输入玩家投影，其他玩家与观战者只看到预备区数量；受支持的玩家传输入口与计时器使用同一合法动作。
- 验证 v1/v2 对同一 state/seed/player 重复 observe、enumerate、simulate 时得到相同 observation、候选
  ID、transition hash 与权威结果；对手 observation 不含 offer 或合法格。
- 验证 AI 的安全格候选、0 安全格无坐标后备、无空格失败关闭、当前 revision、旧 revision和错误玩家；
  planner/self-play 只把 `reserve-deployment` 视为新增结构动作，不因零即时 utility 或普通动作预算错误剪枝。
- 固定 seed 让桌面实时 bot 连续完成至少 3 个自己的渐进部署回合：每回合最多新增 1 枚，部署后直接进入
  既有普通行动，没有旧 skip、非法动作、状态循环或跨回合标签；纯真人房行为不变。
- 验证普通预备核心不阻止终局，extension 中基尔加丹也不阻止终局；仪式召唤后保留核心身份且不获得免费首移标签。
- 验证泰兰德与提里奥每次本人召唤触发、他人召唤不触发；验证没有通用首次上场状态。
- 验证 legacy 显式模式与缺少 mode 的历史状态保持旧部署行为；运行核心规则、房间、公开投影、计时、终局、角色数据、Trace/Replay、类型检查与固定 seed 回归。

### 固定 seed 非 AI 节奏仪器基线

`tests/game/red-138-cadence-baseline.test.ts` 使用 seed `0x138ca11` 在四张正式地图重复执行同一静态脚本：每回合选择 offer 第 1 枚、选择第 1 个权威安全格（没有时走服务端 seeded 兜底），不主动提交普通移动，未使用标签随该部署回合结束清除，并在双方普通预备区耗尽前不战斗；之后仅通过生产 `illidan-demon-strike` 和 `prepareAction` 的权威目标凭证完成击杀。它不导入 AI、不直接修改进行中状态，并对重复执行的完整结果和最终 hash 做一致性检查。

| 度量 | 四张正式地图的固定结果 |
| --- | --- |
| 先手普通预备区耗尽 | 全局第 13 回合 / 完整轮次 7 / 自己第 7 回合 |
| 后手普通预备区耗尽 | 全局第 14 回合 / 完整轮次 7 / 自己第 7 回合 |
| 双方普通预备区全部耗尽 | 第 7 个完整轮次结束 |
| 首次击杀 | 全局第 15 回合 / 完整轮次 8 / 先手自己第 8 回合 |

该基线使用仪器化 5 HP / 100 攻击阵容来隔离流程边界，只证明部署节奏的确定性下界，不代表正式阵容的伤害平衡、真人首杀预测或目标局长。正式的“杀死一个目标”和结束时间标尺仍须基于真人测试另立数值任务。

## 回退方式

1. 停止为新建对局选择 `progressive-reserve-v1`，显式恢复 `legacy-reroll-v1`；不删除模式字段，也不把含双先锋或预备区状态的进行中对局强制转换为 legacy。
2. 已开始的渐进式测试对局应由仍兼容该模式的候选版本完成，或在测试环境明确终止；不得重新抽取先锋、把预备区静默展开成随机场上位置，或在恢复时跳过双先锋初始化屏障。
3. 整体回退 RED-138 的规则、UI、AI Environment、桌面实时 bot 消费者、数据和文档提交即可恢复新建对局旧入口。若只回退 AI 接口，必须同时把实时 bot 房恢复为显式 legacy，不能让 bot 进入无法推进的渐进状态。由于没有数据库或存档版本迁移，不执行破坏性数据降级。
4. 回退不修改 ADR-0004 随机算法、ADR-0011 终局提交边界、ADR-0016 Trace v2 格式、ADR-0019 地图目录或核心经济数值。

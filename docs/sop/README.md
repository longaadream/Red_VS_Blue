# 开发流程与操作规范

状态：有效  
负责人：项目负责人  
适用范围：Human、Codex 及其他项目协作者

本目录用于保存需求、设计、开发、审查、验收、合并和发布流程。

## 标准工作流

每项变更按照以下流程推进：

1. 在 Linear 录入任务。
2. 明确目标、范围和验收标准。
3. 判断风险等级。
4. 确认技术方案和允许修改的路径。
5. 创建独立 Git 分支。
6. 开发并完成自检。
7. 创建 Pull Request。
8. 进行 AI 或人工审查。
9. 完成自动测试或手动验收。
10. 由项目负责人批准合并。
11. 更新文档、版本记录和已知问题。

Linear 使用以下主要状态：

- `Inbox`：刚录入，尚未处理。
- `Need Clarification`：信息不足，不能开始开发。
- `Ready for Dev`：需求和验收标准完整，可以开发。
- `In Development`：正在实现。
- `In Review`：正在检查代码和需求符合度。
- `QA`：正在执行测试和功能验证。
- `Human Approval`：等待项目负责人判断。
- `Ready to Merge`：已经满足合并条件。
- `Done`：已经合并并完成记录。
- `Blocked`：由于明确原因无法继续。
- `Rejected`：验收未通过，需要重新处理。
- `Canceled`：任务不再实施。

## 开发准入条件

任务进入 `Ready for Dev` 前，至少应包含：

- 任务目标。
- 玩家价值或项目价值。
- 本次实现范围。
- 明确不处理的内容。
- 可观察的验收标准。
- 风险等级。
- 受影响模块。
- 允许修改的路径。
- 测试要求。
- 所需验收证据。
- 回退方式。

如果目标、范围或验收标准不完整，AI 只能分析和提问，不能修改代码。

## 风险等级

### Low

适用于文档、文字、非关键 UI、小型独立逻辑和简单修复。

要求：

- 完成相关验证。
- 在 PR 中记录测试结果。
- 由项目负责人批准合并。

### Medium

适用于游戏规则、数值、公共接口、交互流程和依赖变化。

要求：

- 增加测试或可重复的手动验证流程。
- 尽量由另一 AI 或人员进行独立审查。
- 提供状态、截图、日志或回放证据。

### High

适用于存档、经济系统、随机算法、跨模块架构、更新机制和安全代码。

要求：

- 开发前批准方案。
- 提供明确回退方式。
- 验证候选构建。
- 必须由项目负责人批准合并和发布。

## AI 开发规则

AI 实现者负责：

- 阅读任务合同和最小必要上下文。
- 说明理解、风险、修改范围和测试计划。
- 在独立分支完成最小范围修改。
- 添加或更新测试。
- 创建 PR 并提交自检报告。

AI 审查者负责：

- 根据原始任务和验收标准独立检查。
- 重点发现错误、回归、范围越界和测试缺口。
- 引用具体文件、行为或未通过的验收项。
- 不直接复用实现者的结论。

单人开发时，同一个人可以同时负责开发与人工验收。Medium 或 High 风险变更仍应尽量增加一次独立 AI 审查。

## PR 合并条件

合并前确认：

- PR 已关联正确的 Linear 任务。
- 修改没有超出任务范围。
- 验收标准已经逐项确认。
- 测试结果和证据已经记录。
- 所有必要讨论已经解决。
- 相关文档已经同步更新。
- 已知风险和回退方式已经说明。
- Medium 或 High 风险变更已经人工确认。

AI 不得直接合并 `main`，不得绕过保护规则，不得自行发布版本。

## 失败与返工

验收失败时：

1. 指出未通过的具体验收项。
2. 记录期望结果和实际结果。
3. 将任务退回 `In Development`。
4. 只补充与失败项有关的上下文。
5. 修复后重新运行对应测试。
6. 禁止用重复运行掩盖不稳定问题。

## 完成定义

任务只有在以下条件全部满足时才能进入 `Done`：

- 需求已经实现并合并。
- 验收标准已经通过。
- 必要测试已经完成。
- 没有未经说明的范围外修改。
- 文档与代码保持一致。
- 风险和已知问题已经记录。
- Linear、PR 和代码变更可以相互追溯。

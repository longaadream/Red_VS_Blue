## 知识库结构

后续文档按照以下目录整理：

- `docs/product/`：游戏愿景、核心循环、规则、术语和版本目标。
- `docs/technical/`：架构、模块接口、数据结构、存档和调试设计。
- `docs/sop/`：需求、开发、审查、验收和发布流程。
- `docs/decisions/`：重要产品与技术决策记录（ADR）。
- `docs/qa/`：测试场景、回归清单、缺陷和已知问题。
- `docs/README.md`：知识库总入口。

## 信息来源优先级

发生冲突时，按照以下顺序处理：

1. 当前已批准的 Linear 任务及验收标准。
2. 仓库内最新的产品、技术和决策文档。
3. 当前代码和自动测试所表现的实际行为。
4. 旧版本文档、原型和历史实现。
5. 私人聊天记录和口头描述。

如果不同来源发生冲突，不得自行猜测。应记录冲突并交由项目负责人决定。

## 文档维护规则

- 文档使用 Markdown 编写，并与代码保存在同一个仓库。
- 功能行为、公共接口或开发流程发生变化时，同一个 PR 必须更新对应文档。
- 每份文档应注明当前状态，例如：草案、有效、待验证或已废弃。
- 旧文档暂时保留，但必须标明是否仍然适用于当前重构版本。
- 重要架构或规则选择应写入 `decisions/`，避免被反复推翻。
- 文档只描述已经确认的事实；未知内容必须标记为待确认。

## 当前阶段

项目目前处于全面重构阶段：

- 旧版本已经具备基本核心玩法和规则。
- 新版本正在整理结构、修复调试困难并改善主要 UI。
- 当前目标是形成结构稳定、可运行、可邀请玩家测试的 Demo。
- 最新项目代码接管后，需要重新确认旧文档、旧规则和实际实现是否一致。

## 新成员开始工作

新成员或 AI 开始任务前，应依次阅读：

1. 根目录的 `AGENTS.md`。
2. 当前 Linear 任务及验收标准。
3. 本知识库入口。
4. 与任务相关的模块文档。
5. 相关决策记录和测试场景。

只读取当前任务需要的内容，不要默认把整个知识库作为上下文。
